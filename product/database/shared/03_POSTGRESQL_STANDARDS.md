Version: 1.0.0

Status: Enterprise Standard

Owner: Platform Architecture

# Purpose

The PostgreSQL Standards define the physical implementation rules governing every database object within FitnessOS.

These standards ensure every schema, table, column, constraint, index, function, trigger, sequence, and migration follows a consistent enterprise-grade implementation strategy.

All database domains must comply with these standards.

---

# Objectives

The standards ensure:

- Consistent database implementation
- Predictable schema evolution
- Enterprise scalability
- High performance
- Security by design
- AI-friendly code generation
- Simplified maintenance

# Data Type Standards

Choosing the correct PostgreSQL data type is critical for consistency, performance, storage efficiency, and future scalability.

FitnessOS standardizes data types across all domains.

---

# UUID Standard

Primary Keys

Type

UUID

Default

gen_random_uuid()

Purpose

Globally unique identifiers.

Business Rules

All primary keys use UUID.

Surrogate integer primary keys are prohibited.

UUIDs must be generated by PostgreSQL rather than application code unless a specific integration requires otherwise.

---

# Timestamp Standard

Type

TIMESTAMPTZ

Purpose

All timestamps store timezone-aware UTC values.

Required Columns

created_at

updated_at

Optional Columns

deleted_at

approved_at

expires_at

completed_at

cancelled_at

published_at

Business Rules

Application services are responsible for presenting timestamps in the user's preferred timezone.

---

# Date Standard

Type

DATE

Purpose

Calendar dates without time.

Examples

birth_date

hire_date

invoice_date

expiry_date

Avoid storing dates inside timestamp columns when time is irrelevant.

---

# Time Standard

Type

TIME

Purpose

Daily operational time.

Examples

opening_time

closing_time

shift_start

shift_end

---

# Boolean Standard

Type

BOOLEAN

Purpose

Binary business states.

Naming Convention

Prefix with:

is_

has_

requires_

Examples

is_active

is_default

has_access

requires_approval

Avoid storing Yes/No values as text.

---

# Text Standards

Short Text

VARCHAR(n)

Examples

email

code

username

phone

Long Text

TEXT

Examples

description

notes

comments

remarks

Never use VARCHAR without a defined maximum length.

---

# Numeric Standards

Currency

NUMERIC(12,2)

Percentages

NUMERIC(5,2)

Measurements

NUMERIC(10,3)

Quantities

INTEGER

or

NUMERIC

depending on business requirements.

Avoid floating-point types for financial calculations.

---

# JSON Standard

Type

JSONB

Purpose

Flexible structured metadata.

Examples

metadata

preferences

configuration

Business Rules

JSONB should supplement relational data rather than replace it.

Frequently queried attributes should be normalized into columns.

---

# Binary Data

Binary files must never be stored directly inside PostgreSQL tables.

Files should reside in object storage.

Database tables should store only references.

Example

avatar_file_id

document_file_id

attachment_file_id

---

# Enumerations

Business states should use PostgreSQL enums.

All enums must be defined in:

02_ENUM_CATALOG.md

Inline text status columns are prohibited.

---

# Column Naming Standards

Columns use:

snake_case

Examples

organization_id

created_at

membership_status

phone_number

Avoid abbreviations unless they are industry standard.

---

# Required Audit Columns

Unless explicitly documented otherwise, operational tables include:

created_at

updated_at

created_by

updated_by

Soft-delete tables additionally include:

deleted_at

deleted_by

# Required Metadata Column

Every aggregate root and major operational entity includes:

metadata JSONB

Purpose

Supports future extensibility without immediate schema changes.

Metadata must never replace well-defined business attributes.

# Primary Key Standard

Every table must define exactly one primary key.

Type

UUID

Implementation

PRIMARY KEY (id)

Rules

- Composite primary keys are prohibited.
- Surrogate UUID keys are mandatory.
- Business identifiers should use unique constraints rather than primary keys.

Examples

id UUID PRIMARY KEY DEFAULT gen_random_uuid()

---

# Foreign Key Standard

Foreign keys define relationships between entities.

Rules

- Foreign key columns use UUID.
- Foreign key names follow the pattern:

<referenced_entity>_id

Examples

organization_id

branch_id

member_id

invoice_id

Behavior

The appropriate ON DELETE action must be explicitly defined.

Never rely on PostgreSQL defaults.

---

# ON DELETE Standards

CASCADE

Use only when child records have no independent business value.

Examples

user_profile

branch_configuration

RESTRICT

Use when parent deletion would violate business integrity.

Examples

organization

member

invoice

SET NULL

Use for optional historical references.

Examples

approved_by

cancelled_by

deleted_by

---

# Unique Constraint Standard

Business uniqueness must be enforced using explicit unique constraints.

Examples

organization.code

user.email within organization

role.code within organization

Naming

uq_<table>_<columns>

Example

uq_user_organization_email

---

# Check Constraint Standard

Business validation belongs in check constraints whenever possible.

Examples

price >= 0

quantity >= 0

expiry_date > start_date

version > 0

Naming

chk_<table>_<rule>

Example

chk_membership_dates

---

# Default Value Standard

Every default value must represent a valid business assumption.

Examples

created_at

now()

version

1

metadata

'{}'::jsonb

status

active

Avoid defaults that hide business intent.

---

# Nullability Standard

Columns are NOT NULL unless there is a valid business reason for allowing NULL.

Examples

Required

organization_id

created_at

status

Optional

deleted_at

approved_by

notes

Rules

Nullable columns must be intentionally documented.

---

# Soft Delete Standard

Soft deletion is used for business entities requiring historical retention.

Implementation

deleted_at TIMESTAMPTZ

deleted_by UUID

Rules

Soft-deleted records must not appear in normal operational queries.

Deletion does not remove audit history.

Reference data and immutable historical records generally do not support soft delete.

---

# Versioning Standard

Entities requiring optimistic concurrency control include:

version INTEGER

Rules

Initial value

1

Increment on every successful update.

Used by application services for optimistic locking.

---

# Audit Columns Standard

Operational entities include:

created_at

updated_at

created_by

updated_by

Soft-delete entities additionally include:

deleted_at

deleted_by

Historical entities may omit updated_at where records are append-only.

# Schema Organization Standard

FitnessOS uses schema-based domain isolation.

Each schema represents one bounded context.

Examples

platform

membership

hr

attendance

scheduling

commerce

inventory

crm

communication

finance

analytics

integration

Rules

- Tables belong to exactly one schema.
- Cross-schema references are allowed only through documented foreign keys.
- Schema ownership follows the Aggregate Model.

---

# Table Design Standard

Tables model business entities.

Rules

- One table represents one business entity.
- Aggregate roots own their child entities.
- Junction tables model many-to-many relationships.
- Historical entities remain append-only where applicable.
- Configuration entities are updated in place with versioning where required.

Avoid combining unrelated business concepts into a single table.

---

# View Standard

Views expose reusable read models.

Naming

vw_<business_name>

Examples

vw_active_members

vw_branch_revenue

Rules

- Views must not contain business logic.
- Views simplify reporting and querying.
- Views should remain deterministic.

---

# Materialized View Standard

Materialized views support expensive analytical queries.

Naming

mv_<business_name>

Examples

mv_monthly_revenue

mv_member_statistics

Rules

- Refresh strategy must be documented.
- Refreshes should not block operational workloads.
- Use only when measurable performance benefits exist.

---

# Sequence Standard

Sequences are used only where PostgreSQL requires them.

UUID-based tables normally do not require sequences.

Naming

seq_<table>_<column>

Examples

seq_invoice_number

seq_receipt_number

Rules

- Business numbering may use dedicated sequences.
- Primary keys do not use sequences.

---

# Function Standard

Reusable database logic belongs in functions.

Naming

fn_<business_name>

Examples

fn_generate_invoice_number

fn_calculate_membership_expiry

Rules

- Functions should be deterministic whenever practical.
- Business rules remain primarily in application services.
- Database functions should support data integrity and reusable calculations.

---

# Stored Procedure Standard

Procedures execute operational workflows.

Naming

sp_<business_name>

Examples

sp_archive_memberships

sp_refresh_reporting_views

Rules

- Procedures should remain idempotent where practical.
- Long-running procedures should support monitoring and logging.

---

# Trigger Standard

Triggers automate database events.

Naming

trg_<table>_<event>

Examples

trg_member_updated

trg_invoice_created

Rules

- Triggers should remain lightweight.
- Complex business logic belongs in application services.
- Trigger side effects must be documented.

---

# Constraint Naming Standard

Primary Key

pk_<table>

Foreign Key

fk_<table>_<referenced_table>

Unique

uq_<table>_<columns>

Check

chk_<table>_<rule>

Examples

pk_member

fk_membership_member

uq_user_organization_email

chk_membership_dates

---

# Index Naming Standard

Naming

idx_<table>_<columns>

Examples

idx_member_email

idx_invoice_status

idx_attendance_member_date

Composite indexes should list major indexed columns.

# Performance Standards

Performance optimization must never compromise correctness.

Optimization decisions should be supported by measurable evidence rather than assumptions.

---

# Query Design Standards

Rules

- Always select only required columns.
- Avoid SELECT * in production code.
- Queries must use indexed predicates whenever practical.
- Business filtering should occur as early as possible.
- Pagination is mandatory for potentially large result sets.
- Long-running analytical queries should use materialized views where appropriate.

---

# Transaction Standards

Transactions guarantee business consistency.

Rules

- Keep transactions as short as possible.
- Only include statements that must succeed or fail together.
- Avoid user interaction during open transactions.
- Nested transactions should be avoided unless explicitly required.

Isolation Level

Default

READ COMMITTED

Higher isolation levels should be used only where justified by business requirements.

---

# Concurrency Standards

FitnessOS uses optimistic concurrency for most business entities.

Implementation

version INTEGER

Rules

- Version numbers increment after successful updates.
- Update conflicts are handled by the application layer.
- Pessimistic locking should be reserved for exceptional business cases.

---

# Locking Strategy

Locks should be:

- Short-lived
- Predictable
- Minimal

Rules

- Avoid full-table locks.
- Prefer row-level locking.
- Large maintenance operations should execute during maintenance windows.

---

# Batch Processing Standards

Large batch operations should execute asynchronously.

Examples

- Membership expiry processing
- Notification dispatch
- Attendance summarization
- Report generation
- Data archival

Rules

- Batches should support restartability.
- Progress should be measurable.
- Failures should be logged and recoverable.

---

# Error Handling Standards

Database errors should never expose internal implementation details to end users.

Rules

- Errors should be logged with sufficient diagnostic information.
- Business validation errors should be distinguished from infrastructure failures.
- Constraint violations should be translated into meaningful application responses.

---

# Retry Strategy

Transient failures may be retried.

Examples

- Deadlocks
- Temporary network interruptions
- Connection pool exhaustion

Rules

- Retries should use exponential backoff.
- Infinite retries are prohibited.
- Non-idempotent operations require special handling.

---

# Backup Strategy

Backups are mandatory.

Minimum Requirements

- Daily full backups
- Continuous WAL archiving
- Automated backup verification
- Regular restoration testing

Retention periods are defined in:

10_DATA_RETENTION_POLICY.md

---

# Disaster Recovery

The platform must support recovery from:

- Hardware failure
- Database corruption
- Accidental deletion
- Infrastructure outage

Recovery objectives should be defined according to deployment requirements.

---

# Monitoring Standards

Operational databases should be monitored for:

- Query performance
- Lock contention
- Connection utilization
- Replication health
- Disk usage
- WAL growth
- Index usage
- Table bloat

Alerts should be generated before operational thresholds are exceeded.

---

# Logging Standards

Database logging should capture:

- Critical errors
- Slow queries
- Deadlocks
- Failed authentication attempts
- Backup failures

Sensitive business data must never appear in logs.

---

# Maintenance Standards

Routine maintenance includes:

- VACUUM
- ANALYZE
- REINDEX where necessary
- Statistics updates
- Partition maintenance
- Backup verification

Maintenance tasks should be automated whenever practical.

---
