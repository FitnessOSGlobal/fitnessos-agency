# ATTENDANCE DATABASE SCHEMA ARCHITECTURE

Version: 1.0.0

Status: Draft

Owner: Database Architecture

---

# Purpose

This document defines the PostgreSQL schema architecture for the Attendance Domain.

It translates the business entities and aggregates into a logical database organization while preserving domain ownership and supporting long-term scalability.

The Attendance Domain owns all attendance-related persistence objects.

---

# Schema Name

attendance

---

# Schema Ownership

Owns:

- attendance_sessions
- attendance_events
- access_devices
- gate_events

The Attendance schema is the only schema permitted to modify these tables.

---

# External References

The Attendance schema references identifiers owned by other domains.

## Platform

- organization_id
- branch_id
- user_id

## Membership

- member_id
- membership_id

Attendance never owns or duplicates these entities.

---

# Table Architecture

attendance

├── attendance_sessions

├── attendance_events

├── access_devices

└── gate_events

---

# Relationships

attendance_sessions

↓

attendance_events

↓

gate_events

access_devices

↓

attendance_events

Cross-schema references exist only through foreign keys.

---

# Primary Keys

All tables use:

UUID

Generated by PostgreSQL.

---

# Foreign Keys

Attendance references:

Platform

- organizations
- branches
- users

Membership

- members
- memberships

No circular ownership is permitted.

---

# Audit Strategy

Every table includes standard audit fields:

- created_at
- updated_at
- created_by
- updated_by

Business events additionally include immutable event timestamps.

---

# Indexing Strategy

Primary indexes:

- Primary Key
- Foreign Keys
- Event Timestamp
- Check-In Timestamp
- Branch Identifier
- Member Identifier
- Session Status

Composite indexes will optimize:

- Occupancy
- Visit History
- Daily Attendance
- Peak Hour Reporting

---

# Multi-Tenant Strategy

Every business table contains:

organization_id

Tenant isolation is mandatory for every query.

Cross-tenant joins are prohibited.

---

# Retention Strategy

Attendance history is retained permanently unless organizational retention policies require archival.

Operational deletes are not permitted.

Historical records may be archived but must remain recoverable.

---

# Performance Considerations

The schema is optimized for:

- High write throughput
- Concurrent check-ins
- Historical reporting
- Real-time occupancy
- AI analytics
- Event sourcing compatibility

---

# Future Expansion

Future tables may include:

- visitor_sessions
- occupancy_snapshots
- parking_sessions
- wearable_events
- facility_zone_events

These additions must preserve existing schema boundaries.
