# Purpose

This document provides the implementation specification for the Attendance Domain database.

It defines the database objects, ownership, relationships, constraints, indexing strategy, and implementation rules required to build the Attendance persistence layer using PostgreSQL and Drizzle ORM.

This document is the authoritative reference for implementation.

---

# Schema

attendance

---

# Owned Tables

The Attendance Domain owns the following tables:

| Table | Purpose |
|--------|---------|
| attendance_sessions | Member visit lifecycle |
| attendance_events | Business attendance events |
| access_devices | Physical and digital access devices |
| gate_events | Raw access control events |

Only the Attendance Domain may modify these tables.

# Attendance Sessions

Purpose:

Represents a complete member visit.

Required attributes include:

- Session Identifier
- Organization Identifier
- Branch Identifier
- Member Identifier
- Membership Identifier
- Check-In Timestamp
- Check-Out Timestamp
- Visit Duration
- Session Status

Business Rules:

- Exactly one successful check-in starts a session.
- Exactly one successful check-out completes a session.
- Sessions cannot overlap for the same member unless explicitly allowed by business policy.
- Completed sessions are immutable.

---

# Attendance Events

Purpose:

Stores operational attendance events.

Required attributes include:

- Event Identifier
- Session Identifier
- Device Identifier
- Operator Identifier
- Event Type
- Event Timestamp
- Validation Result

Business Rules:

- Events are append-only.
- Events cannot be updated.
- Events cannot be deleted.

---

# Access Devices

Purpose:

Represents hardware or software used for access validation.

Required attributes include:

- Device Identifier
- Device Name
- Device Type
- Branch Identifier
- Firmware Version
- Operational Status

Business Rules:

- Devices belong to one branch.
- Historical device references must remain valid even after retirement.

---

# Gate Events

Purpose:

Stores raw events generated by access hardware.

Required attributes include:

- Gate Event Identifier
- Session Identifier
- Device Identifier
- Raw Payload
- Authentication Result
- Device Timestamp
- Synchronization Status

Business Rules:

- Immutable history.
- Failed authentication attempts are retained.
- Raw payloads are preserved for diagnostics.

---

# Foreign Key Rules

Attendance references:

Platform

- organizations
- branches
- users

Membership

- members
- memberships

Cross-domain ownership is prohibited.

---

# Indexing Strategy

Indexes are required for:

- organization_id
- branch_id
- member_id
- membership_id
- session_status
- check_in_at
- check_out_at
- event_timestamp
- device_id

Composite indexes should support:

- Occupancy calculations
- Visit history
- Daily attendance
- Peak-hour reporting
- Member activity analysis

---

# Multi-Tenant Rules

Every business table includes:

organization_id

Tenant isolation is mandatory.

Cross-tenant queries are prohibited unless explicitly authorized for platform administration.

---

# Retention Policy

Attendance records are retained indefinitely unless organizational retention policies require archival.

Operational deletion is prohibited.

Archival must preserve referential integrity and audit history.

---

# Performance Targets

The Attendance database must support:

- High-frequency concurrent check-ins
- Real-time occupancy reporting
- Historical analytics
- AI-driven attendance insights
- Branch-level reporting

---

# Implementation Notes

Implementation sequence:

1. Drizzle Schema
2. Migration
3. Repository
4. Service
5. Controller
6. Tests

This sequence must be followed for all Attendance aggregates.
